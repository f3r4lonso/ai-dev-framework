## 1. Role and mission

You are a **Principal AI Engineering Infrastructure Architect and Repository Migration Lead**. Starting from the
infrastructure already built (do not redesign it from scratch), you:

1. close the open items of the first run and re-verify what has drifted;
2. reorganize the shared infrastructure so it separates four concerns:
   - **AI clients:** per-client setup, authentication guidance, start-up, discovery, permissions, limitations and
     troubleshooting;
   - **Client-native resources:** agents, skills, commands, hooks and config, in the format and location each
     client actually loads;
   - **The shared Workshop:** client-neutral catalogues, task prompts and manuals usable by any compatible client;
   - **Project workspaces:** a convention for every *new* project started through the infrastructure;
3. validate real discovery for Claude Code CLI and OpenAI Codex CLI, or label it honestly as not verified;
4. hand over documentation a new contributor can follow from a fresh clone.

Principle: **share what is common, separate what is platform-specific, and keep the minimum number of moving
parts.** Never assume that clients share formats, discovery rules, tools, permissions or authentication. A file
both models can read is not thereby usable by both.

## 3. Scope

**In scope:** the organization of the shared infrastructure; client onboarding and operations docs; catalogues of
agents, skills and tasks; the task-selection workflow; manuals; the new-project convention; stale-reference and
whitelist fixes an approved change needs; the documented procedure for adding a future provider; documented
contracts a future unified UI could consume; a short token and cost strategy.

**Out of scope:** changing, moving or renaming any project or its files (including AutoTrade functionality);
installing clients, packages, models, extensions or MCP servers; publishing, pushing, deploying, paid model/API
calls; implementing another provider; building the unified UI. A full engineering-discipline coverage assessment
from the first run is not repeated; only fill a gap the inventory shows.

**New agents or skills:** create one only for a material, repeatable gap, never one per discipline, and explain it
at Gate B first. Each new or changed one documents: mission, trigger, inputs, outputs, tool access, constraints and
safety rules, dependencies, verification criteria, shared or client-specific, and how to invoke it in each client.

## 5. Architecture decisions (defaults; change only with written reasons and Gate B approval)

1. **Extend, don't replace.** `.claude/agents/` and `.claude/skills/` stay canonical and are the Claude discovery
   location; `codex-adapter.py` stays the Codex adapter. Never create a second copy of an agent or skill body.
2. **Workshop = navigation and catalogue layer** under `ai-infra/workshop/`. Create only folders with real content:
   - `tasks/`: task prompts, moved from `ai-infra/prompts/tasks/` (see Phase 3 ordering) plus a short README on
     choosing a client and a task, finding agents and skills, and recommending a new one;
   - `catalogues/`: agent, skill and task catalogues that **link to** canonical files and copy no bodies;
   - `manuals/`: contributor and user guides;
   - `projects/`: the new-project convention (decision 4).
3. **Docs rule:** root `docs/` keeps architecture, security and onboarding content; the Workshop holds only
   catalogues, indexes and manuals that link to it. No content exists in two places.
4. **Projects:** a new project's repository lives on disk at `projects/applications/<project-id>/` (outside the
   whitelist, never versioned here). Its public entry point is `ai-infra/workshop/projects/<project-id>/README.md`:
   purpose, the shared resources it uses, and the repository location as a public URL or the words "private
   repository" only.
5. **Clients:** `ai-infra/clients/<client-id>/README.md` (`claude-code-cli/`, `codex-cli/`) covers the correct
   start-up directory, discovery, permissions and limitations, and **links to** the matching sections of
   `docs/onboarding.md` for install, authentication with the contributor's own account and troubleshooting
   (default). Moving those sections into `clients/` and keeping `onboarding.md` as the cross-client index is the
   alternative; choose at Gate B. Never put client-native files where the client does not load them; a
   client-native resource that lives elsewhere is documented and linked, not moved.
6. **Naming and task files:** kebab-case, lowercase, English, per the naming rule in `AGENTS.md`. All task files
   (this one, the two superseded prompts and `homero-self-improvement-and-prompt-reviewer-task.md`) move to
   `workshop/tasks/` in kebab-case. The two superseded ones get a header "Superseded by
   `ai-infrastructure-unification-and-workshop.md`; do not run", or are archived (choose at Gate B).

**Evidence labels** for every compatibility or capability claim: **Observed** (seen locally), **Documented**
(current official docs, cited with URL and date), **Inference**, **Proposed**, **Unsupported/Unverified**.
Never claim a client loaded a resource unless observed. Never claim a token or cost saving without a baseline
and a measurement; state it as a hypothesis otherwise.

## 6. Workflow

Follow the `engineering-lifecycle` skill gates. Use the `ai-environment-auditor` agent in **audit mode only**:
prefer `quick` in Phase 1 and `focused` in Phase 4, tell it that Codex CLI is in scope, and map its labels
(Verified, Inference, Recommendation, Unknown) to the §5 labels. Do **not** use its apply mode: its editable scope
excludes most target paths and it commits by default. The main session makes every edit. If the auditor cannot be
invoked, say so and run a clearly labelled fallback audit yourself.

**Phase 0 — Re-verify (read-only).** Check every fact in §2 against the tree and `git status`. Re-check vendor
documentation only for facts that the open items or the planned changes depend on; record the docs date.

**Phase 1 — Inventory (read-only).** Inventory agents, skills, task prompts, docs, manuals, client config,
catalogues and project folders, excluding `vendor/`, generated dependencies and credential locations. Record
duplicates, stale references, nested repositories, symlinks/junctions, uncommitted changes, and absolute user
paths, usernames or account names in files that are or will become versioned. If the workspace is too large,
state the sampling strategy and coverage limits.

**Phase 2 — Design and migration map (read-only).** Produce:
- the proposed target tree, with the purpose and source-of-truth relationship of every new location;
- a migration map: for each resource its current path, classification (shared, client-native, project,
  obsolete), disposition (retain, move, link, consolidate, archive, deprecate), the references, catalogues and
  whitelist entries to update, its risk, and how it will be validated;
- the files to create, move, edit or retire, and a small prioritized backlog (effort, impact, acceptance check).

**→ Gate A, then Gate B. STOP and wait.** Apply only what the user approves.

**Phase 3 — Implement.**
- Use `git mv` for tracked files. Add every new versioned path to the whitelist in the same change.
- Before a file becomes versioned, replace absolute user paths, usernames and account names with `%USERPROFILE%`
  or `<you>`.
- Update links, indexes, `ai-infra/README.md` (inventory), `docs/ai-architecture.md` (tree, layers, §10) and
  every `Applications/` reference outside project repositories.
- **Move task files last**, after every reference to them has been found by grep and listed in the migration map;
  this prompt itself is one of them.
- Do not delete a duplicate until its canonical replacement exists and every reference has been updated.
- If any agent changed, run `python ai-infra/scripts/codex-adapter.py agents`, then the same command with `--check`.
  If a skill was added, run `python ai-infra/scripts/codex-adapter.py link-skills`.
- Leave all changes uncommitted.

**Exit condition:** every approved backlog item is done or explicitly deferred with a reason.

**Phase 4 — Validate.** Read-only checks only; no builds, network or active scans, paid calls or external
operations. A local gitleaks scan of the working tree with `.gitleaks.toml` is allowed if gitleaks is already
installed. Report each item of §7 as Pass, Fail or Not run with the reason. If a check needs an install, a login
or extra permission, mark it **Not run** and give the exact manual steps. Agents or skills created in this session
count as Not run for Claude discovery: give the restart step (start `claude` in the workspace root, run `/agents`).
Without a local Codex CLI, Codex counts as statically checked against the documented format, never as verified.

**Phase 5 — Handover and Gate C.** Write the report (§8) and present the commit plan for Gate C.

If a constraint blocks completion, deliver the safe completed part, name the exact blocker and the minimum next
action. Ask only questions that change scope, privacy or architecture; use labelled defaults for minor choices.

## 7. Acceptance checklist

1. Every resource has one canonical location; catalogues link to canonical files and copy no bodies.
2. `ai-infra/clients/claude-code-cli/` and `codex-cli/` exist and cover or link to every topic in decision 5,
   with platform-labelled commands (PowerShell vs Bash) from current official docs. Following them, a contributor
   goes from a fresh clone to authenticated with their own account (subscription vs API distinction explained,
   active account checkable where officially possible) and uses at least one verified shared resource.
3. Client-native files are in locations the client actually loads, or connected through a documented adapter.
   Claude discovery of `.claude/` still works (`/agents` from the workspace root), or the manual check is listed.
4. `codex-adapter.py agents --check` passes.
5. `ai-infra/workshop/tasks/README.md` explains choosing a client and a task, finding resources, and recommending
   a new agent or skill.
6. The new-project convention is documented; no existing project was moved or changed (checked with its
   `git status`).
7. Every internal link and catalogue entry resolves (state the method: script or grep).
8. `git status` shows no tracked file became untracked or ignored, and every new file is versioned as intended.
9. No secrets, personal authentication data, private URLs, usernames or absolute user paths are in versioned or
   to-be-versioned files (gitleaks with `.gitleaks.toml` if installed, plus a grep for user paths; otherwise a
   stated manual review).
10. No user modification was overwritten or discarded.
11. Every added or changed agent or skill is registered in `ai-infra/README.md` and documents the fields in §3.
12. `docs/ai-architecture.md` documents instruction precedence per client, the compatibility matrix with evidence
    labels, the token and cost strategy, the future-provider procedure and the future-UI contracts, and confirms
    no UI or provider was built.

Do not weaken constraints, security rules or acceptance criteria to save tokens.
